*rtlbuddy.txt*  Neovim adapter for rtl-buddy-hub

==============================================================================
INTRODUCTION                                            *rtlbuddy* *rtlbuddy.nvim*

rtlbuddy.nvim is the source-side participant in the rtl-buddy visualisation
mesh. It connects to a running `rtl-buddy-hub` over TCP, broadcasts the
cursor's file/line/column on demand, and services hub-originated requests
(open_source) to keep this nvim instance in sync with the schematic viewer
and surfer.

The plugin COMPOSES with verible-verilog-ls. It never overrides <C-]> and it
never claims the LSP diagnostics namespace.

==============================================================================
COMMANDS                                                *rtlbuddy-commands*

                                                                *:RtlBuddyShow*
:RtlBuddyShow        Broadcast `source_focused` for the cursor's
                     {file,line,col} to the hub.

                                                                *:RtlBuddyOpen*
:RtlBuddyOpen {f} {l} [{c}]
                     Open file {f} and jump to line {l}, column {c}.
                     Usually invoked by the hub via RPC.

                                                              *:RtlBuddyToWave*
:RtlBuddyToWave      Send `wave_add_variables` for the symbol under the
                     cursor.

                                                              *:RtlBuddyDomain*
:RtlBuddyDomain      Show hub-resolved overlay info at the cursor in a
                     floating window.

                                                              *:RtlBuddyStatus*
:RtlBuddyStatus      Print hub connection state and registered peers.

                                                                *:RtlBuddyPhys*
:RtlBuddyPhys        Toggle the phys annotation (a module's cells, area and
                     instance power as virtual text at its declaration).

                                                         *:RtlBuddyPhysRefresh*
:RtlBuddyPhysRefresh Re-read the physical model for this buffer's project and
                     redraw. The read is cached for the session, so this is
                     how a `rb synth` / `rb power` run in another terminal
                     becomes visible.

==============================================================================
KEYMAPS                                                 *rtlbuddy-keymaps*

Default (opt-out via `setup({keymaps = { show = nil, ... }})`):

  <leader>rs    :RtlBuddyShow
  <leader>rw    :RtlBuddyToWave
  <leader>rd    :RtlBuddyDomain
  <leader>wa    add signal under cursor to Surfer (when launched via `rb wave`)
  <leader>rp    :RtlBuddyPhys (toggle the phys annotation)

<C-]> is left to LSP go-to-definition.

==============================================================================
SETUP                                                   *rtlbuddy-setup*

>lua
    require("rtlbuddy").setup({
      auto_connect = true,
      use_lsp_for_symbol = true,
      augment_lsp_hover = false,
      diagnostics_namespace = "rtlbuddy",
      keymaps = { show = "<leader>rs", to_wave = "<leader>rw", domain = "<leader>rd" },
      wave = { annotate = true, keymap = "<leader>wa" },
      phys = { annotate = true, keymap = "<leader>rp" },
    })
<

`wave.annotate` shows the `rb wave` signal value (WAVE_VALUE) as inline virtual
text on launch; `wave.keymap` adds the signal under the cursor to Surfer via the
WAVE_CTRL_SOCK control socket. Set either to false/nil to disable.

`phys.annotate` draws the physical numbers described below; `phys.keymap` maps
the toggle. Set either to false/nil to disable.

==============================================================================
PHYS ANNOTATION                                         *rtlbuddy-phys*

With `phys.annotate` (the default), each `module <name>` declaration line in a
verilog/systemverilog buffer gets end-of-line virtual text with that module's
physical numbers, in the `RtlBuddyPhys` highlight: >

    module alu (            ▸ 1 234 cells · 72.1 µm² · 15.2 µW
<
The numbers are read from the artefacts `rb synth` and `rb power` left on disk
(rtl_buddy >= 6.49.0), by two machine-mode reads run in the buffer's project
root:

  `rb --machine phys summary --limit 0`    every module's cells and area
  `rb --machine phys module <name>`        that module's instance power

No hub connection is involved and nothing crosses the hub wire. Both reads are
asynchronous (`vim.system`) and debounced, the summary is cached per project
root for the session, and the annotation refreshes on `BufEnter` and
`BufWritePost`.

Parts are omitted rather than guessed at:

  * no cells/area for a module the synthesis half has no row for;
  * no power unless `rb phys module` attributes it to that name without a
    caveat. The power half's `module` column names Liberty *cells*, not RTL
    modules, so until rtl_buddy's hierarchy join lands (rtl_buddy#558) most
    RTL modules show cells and area alone;
  * no mark at all for a module neither half of the model knows.

When `rb` is not on `PATH`, the project has no physical model, or the verb
refuses, there are no marks and one |vim.notify()| at DEBUG level; the
standing answer is in `:checkhealth rtlbuddy`.

Own namespace (`rtlbuddy_phys`) and highlight group, distinct from the wave
annotation's and from the `rtlbuddy` diagnostics namespace. Issue:
rtl-buddy/rtl-buddy-nvim#12 (rtl-buddy/rtl_buddy#596 §2).

==============================================================================
HEALTH                                                  *rtlbuddy-health*

`:checkhealth rtlbuddy` reports Neovim version, hub state, LSP attach status,
whether wave annotation is enabled, and whether the phys annotation is enabled
and has `rb` on `PATH` to read from.
